## Context

`mifos-x-open-banking` is a Kotlin Multiplatform client for the UK Open Banking (OBIE) standard,
targeting the HSBC UK Personal sandbox across Android, iOS, Desktop and Web.

Several structural decisions were taken during project setup and recorded only as fields in
`idea-plan.yaml#§technical_decisions`. Fields capture *what* was chosen but not *why*, and the
reasoning is what a future contributor needs — particularly where a choice looks arbitrary but is
load-bearing.

Two forces make this acute here:

1. **The project owns no backend.** It consumes an API operated by a bank under a regulated
   standard. Decisions that would normally be revisitable — data shape, auth mechanism, error
   vocabulary — are fixed by OBIE and FAPI, and a contributor needs to know which constraints are
   ours and which are the standard's.
2. **The scope changed materially after setup.** The 2026-07-30 reversal moved PISP domestic single
   payments from out-of-scope to in-scope, turning a strictly read-only app into one that moves
   money. That invalidated assumptions baked into the original decisions.

---

## Decision

**We will record architecture decisions in this directory as numbered ADRs**, in the format
described by Michael Nygard, one file per decision, immutable once Accepted (superseded by a new
ADR rather than edited).

The decisions in force at the time of writing, from `§technical_decisions`:

| Decision | Choice | Why it is not arbitrary |
|---|---|---|
| Architecture | **MVI, stream-first** — `BaseViewModel<S,E,A>` + `ScreenDataStream` + Store5 | The repository is a stateless gateway; the **ViewModel** owns the stream. Repositories are Koin `single`s, so per-screen state in one is a bug |
| DI | **Koin** (+ koin-annotations) | Feature modules register `viewModelOf`; `SavedStateHandle` is supplied with no extra wiring |
| State management | **Compose state** | UI collects `stateFlow`; `trySendAction` only enqueues onto a channel drained in `viewModelScope` |
| Navigation | **androidx-navigation**, type-safe `@Serializable` routes | A route's property name must equal the `SavedStateHandle` key |
| Backend provider | **REST** — external, not owned | `backend.owned: false`; `server-layer/` holds client contracts, never schema |
| Platform targets | **Android · iOS · Desktop · Web** | Forces `expect`/`actual` for mTLS, secure storage and app-to-app redirect |
| KMP arch | **`stream-first@latest`** | Inherited from `kmp-project-template`; `core-base/*` is consumed, never modified |

## Consequences

**Positive**

- One state contract across 18 features. A contributor who learns `direct-debits` can read any
  account-scoped screen.
- Stateless repositories make per-screen streams trivially testable against a fake.
- `core-base/*` being off-limits keeps the template upgradeable — modified exactly once
  (`ScreenDataStream`'s constructor made public, commit `c27c10a`).

**Negative / accepted costs**

- The stream-first shape does not fit every screen. Three documented exceptions —
  `AccountsOverviewRepository` (holds stream state), `ProductRepository` (storeless one-shot,
  because product terms must never be cached) and `transactions` (suspend cursor-pager) — each
  needs a comment explaining why it deviates, or a contributor copies the wrong template.
- Four platform targets multiply every platform-touching decision by four, and the `wasm/js` test
  tasks are disabled project-wide (skiko/KT-67468).
- Not owning the backend means error vocabularies are the bank's. `U000`, `U019`, `U009` and their
  meanings are external facts the client must encode.

**Open — and this ADR does not settle it**

> **PISP is a distinct FCA permission from AISP.** Sandbox operation is unaffected, but production
> payment initiation would require authorisation this project does not hold. All three P3 features
> carry `adr_required: true` and the decision has **not** been recorded.
>
> This ADR is generated from `§technical_decisions` and covers the *technical* stack only. The
> regulatory position needs **ADR 0002**, hand-written, covering: whether the app ships PISP to
> production at all, what the sandbox-only boundary is, and who holds the permission if it does.
> Do not treat this file as satisfying that requirement.
