**The app's first WRITE phase.** P0 through P2 are entirely read-only AIS, which is why the four
prerequisites below are cross-cutting infrastructure rather than per-feature work.

#### Prerequisites — none is per-feature, all four gate the whole phase

| # | Prerequisite | Current state in source |
|---|---|---|
| 1 | `core/network/api/Pisp.kt` — Ktorfit interface for the five PISP endpoints | **absent** — `core/network/api/` ships only `Aisp.kt` and `OAuth.kt`; zero references to `/domestic-payments` |
| 2 | Detached JWS (PS256, `b64:false` + `crit`) extending the shipped `signPs256` | **absent** — zero references to `x-jws-signature`. Without it **every write returns `400 U019`** |
| 3 | `x-idempotency-key`, persisted across retries of a staged payment | **absent** — zero references |
| 4 | Payments-scope client-credentials token path | **partial** — `ConsentCreationScope.PAYMENTS` already exists at `OAuth.kt:103`; no caller passes it |

**Nothing in P3 can be device-verified until #2 lands.** Every PISP write fails at the signature
check before reaching business logic, so a feature could look complete in code and be untestable
against the sandbox.

#### What already exists, and is easy to miss

The **wire models ship in full** — 130 DTO files under `core/network/.../model/pisp/` covering all
six OBIE payment types (domestic/international × single/scheduled/standing-order), request and
response. `domesticPayment/` alone provides `DomesticPaymentConsentRequest`, `DomesticPaymentRequest`,
`Initiation`, `InstructedAmount`, `CreditorAccount`, `DebtorAccount`, `Risk` and
`RemittanceInformation`, plus the response side with `Links` and `Meta`.

The remaining P3 work is therefore the API surface, the two headers and one caller — **not** a DTO
layer. That unconsumed surface is precisely what motivated the scope reversal: the models and the
`SendMoneyRoute` placeholder both already pointed at payment initiation.

#### Regulatory gate

PISP is a **distinct FCA permission** from AISP. Sandbox operation is unaffected; production payment
initiation would require authorisation this project does not hold. All three P3 features carry
`adr_required: true`.

> **The ADR does not exist yet.** `adr/0001-record-architecture-decisions.md` is the doc-set's only
> ADR entry and is generated from `§technical_decisions`; the PISP regulatory decision needs its
> own record and has not been written.
